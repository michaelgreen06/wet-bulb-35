# Five-day forecast provider-miss verification

Proposed follow-up to the current-conditions Turnstile rollout. The existing hostname-restricted widget, Siteverify secret, verified action (`weather_refresh`) and signed 24-hour pass are shared. This PR does not create a new widget, per-requester budget, WAF rule, DNS record or provider license. Deployment is a separate approval; the current production Worker is unchanged until then.

- Only a resolved canonical city's `/api/forecast` can be queried. Known crawler UAs return `204`. Fresh results are public. Stale results remain readable, but unverified requests cannot trigger a background Open-Meteo refresh.
- On a cold edge cache miss, a read-only lookup in the existing WeatherGate Durable Object may supply a valid same-run result without a challenge. Otherwise enforcement requires a valid 24-hour pass or Siteverify success before calling `/forecast` in the gate (the only route that can spend provider budget). Failed, forged and expired tokens, incorrect hostname/action, Siteverify outages and missing enforcement configuration cannot refresh the provider.
- The client lazily renders the existing Managed widget only after `403 verification_required`, sends the one-use token in a header and retries once. City HTML remains indexable and the forecast can show unavailable without hiding the page.
- The signed pass cookie changes from `Path=/api/weather` to `Path=/api` to cover both current conditions and forecasts. Existing weather-only cookies continue to work for weather, but forecast needs one new verification before obtaining a shared pass; a browser may temporarily send both cookie paths for weather, so both are checked. The pass is not an identity or a per-visitor quota.
- Check both a cold forecast and current-conditions page in a real browser under the approved staging hostname and an actual widget/secret before a production rollout. Verify cached/stale reads, DO read-only peek, rejected token, shared cookie, mobile widget, unchanged canonical pages and provider-budget telemetry. Keep the current production version available for rollback and start a new monitor only after explicit deployment approval. Rollback on genuine core failures, never on provider-weather warning or sitemap inventory drift.
