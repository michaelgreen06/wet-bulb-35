# All-location city enrichment: requested fields and implementation order

**Status: proposed plan only.** Michael's target is all eight fields below on every canonical location page where validated source data exists. The sequence is an **implementation order by difficulty**, not a reduction of the final page requirements. The three modeled historical-high products are last because they need full-period hourly acquisition and validation. This document does not authorize downloading source data, indexing submissions, route changes, PR merge, staging, or production deployment; each implementation/release is reviewed separately.

Google Search Console currently cannot reliably answer whether enrichment is worth doing after the September 20 canonical resubmission and manual indexing requests. **Assume useful all-page enrichment is worth pursuing.** GSC measurement is optional monitoring, never a prerequisite to implementing the fields. Quality, provenance, storage, backup, staging and release gates still apply. Do not imply enrichment guarantees indexing.

## Required fields, easiest useful work first

1. **Location population — near-term.** The existing GeoNames-derived population sidecar covers 130,041 of 130,686 inventory rows, but is keyed by coordinate and currently supports nearby-link ranking, not city-page population display. Convert verified matches to canonical-path/stable-ID-keyed city facts; inspect shared coordinates, namesakes and ambiguous/remaining rows before rendering. Show the GeoNames settlement population with source/snapshot date—not an unlabeled current metro estimate. Missing/uncertain values are unavailable, never zero or guessed. No new population provider is required for the verified subset. Reuse the existing sidecar as input, not its coordinate key as long-term identity.
2. **Local time — near-term once timezone identity is verified.** A private GeoNames identity/timezone join already exists for most routes; finish/review unmatched and ambiguous routes without altering their URLs. Put each validated IANA timezone in the compact city-facts asset. Render a stable label in crawlable HTML, then run a small browser clock with `Intl.DateTimeFormat({ timeZone })`, updating on a timer and when the tab resumes. Never freeze a current time in 24-hour cached HTML or use the visitor's timezone. Test half-hour offsets, daylight-saving transitions, date rollover, and unsupported/missing zones; show unavailable for unresolved routes. No weather API call is needed for the clock.
3. **Location elevation — near-term with per-record quality checks.** Read GeoNames `elevation`, falling back to `dem` only when the source field is absent and retaining which was used. Validate units, sentinel/NoData, implausible values and coast/high-terrain exceptions; quantify coverage before asserting an all-city number. Show an approximate **point** elevation and provenance, not the mean elevation of a city or metro. Omit where unsupported. Share the population/timezone identity pass and compact city-facts asset.
4. **Climate classification — moderate expansion.** Extend the already pinned Popular-40 Beck et al. 1991–2020 Köppen-Geiger raster sampler offline to all verified route coordinates. Preserve the center-cell and 3×3-neighborhood agreement/modal-share gate; return a per-route boundary-sensitive/NoData state rather than lowering the threshold or failing an entire all-city run because one coastal cell is unavailable. Pin raster/legend hashes, retain class/source period, review coast, island, mountain, border and diverse-climate samples. Render a plain-language class with attribution; it does not measure wet-bulb risk.
5. **Average wet bulb temperature for each month — moderate-to-hard expansion.** Keep the existing Popular-40 NASA POWER `T2MWET` 1991–2020 modeled **monthly means** and labels; do not silently change those values to ERA5-Land or call monthly means historical highs. The current generator is hard-coded to 40 reviewed point responses, so a 130,686-page rollout needs a new bounded offline acquisition pipeline: map canonical coordinates to actual NASA grid cells; benchmark the official regional climatology endpoint and compare its cell values with the pinned point samples; acquire/cache each needed cell or region once with rate/size limits; validate all 12 months, units, time basis, fill values, period and checksums; pack values in compact versioned shards. NASA regional climatology allows one parameter per request, enough for `T2MWET`, but real global throughput/fair use and source-cell reuse must be measured before choosing a download schedule. Display shared cells as modeled grid-point values in local solar time, with peak months and the established source notes—not as unique city observations.

The first three fields can become an **initial city-facts PR** using existing verified sources, followed by a **climate + monthly-means PR** after its offline sampling and ingestion benchmarks. These are implementation slices, not a demand to wait for all eight before giving people useful reviewed facts. The current five-day wet-bulb forecast already appears on all canonical city pages and remains separate from these fields.

## Required historical fields — last to implement, not optional

6. **Historical modeled high wet bulb for each of the 12 months.** Calculate maxima from the same complete, simultaneous ERA5-Land hourly temperature, dew point and surface pressure series used below, with the winning timestamp and local month, not from NASA POWER's monthly means. Require the stated source period and full coverage.
7. **Highest modeled wet bulb for the location over the stated period.** Show its local date/time and exact complete ERA5-Land period (starting in 1950 where valid, ending at the last validated complete year). It is neither an official observation nor an unqualified “all-time” record. Do not combine ERA5, station or ERA5-Land maxima.
8. **Historical modeled high for today's local calendar day.** Build 366 month/day entries from validated complete local dates and the same hourly series. The displayed date changes at the location's midnight independently of cached HTML. Keep February 29, 23-/25-hour daylight-saving days and source-period boundaries correct.

The open offline historical pipeline PR #41 has complete **research-only** periods for ten unmasked cities, not publishable all-city data. Historical publication still needs upstream chunk-byte pinning, a scalable and fair-use-bounded tile/year backfill, full-period coverage and modeled-cell QA, manual same-landmass nearest-land-cell review within 15 km for masked coasts (or unavailable), compact history shards keyed by actual source cell **and timezone**, Worker-memory/runtime testing, and a separately approved release. Station data is excluded from v1. Store private source chunks and checkpoints outside Git; never fetch historical source data on page requests. Do not assert that static assets alone will work until a representative full-size staging benchmark passes; request a read-only storage binding only if measured limits require it and Michael separately approves it.

## Shared rollout checks (no GSC success gate)

- Freeze the current canonical inventory and stable city identity before generating facts. Every route must resolve to one reviewed record **or an explicit field-specific unavailable reason**; do not change URLs, re-sort country/region directories, introduce duplicate canonicals, or copy one city/metro identity to a namesake.
- Keep raw GeoNames, raster, NASA and ERA5-Land sources private and checksum-pinned. Publish only compact derived records, source/version manifest and deterministic validators. Reject source changes and ambiguous identity; do not mask them with generic prose or fabricated values.
- Render static facts and monthly climate values in crawler-readable HTML without provider calls. The live clock and today's historic-high selection may hydrate in the browser, but their source facts and labels must stay clear and cache-safe. Keep attribution near the values, and current weather/forecast behavior unchanged.
- Benchmark per-asset bytes, shard count and parsed Worker memory against the actual Cloudflare constraints; test large-country and diverse-country reads, renderer/asset parity, accessibility and mobile layout. Stage each approved slice before a separately approved merge/production release with backup, rollback and monitoring.
- GSC can be revisited later for observation, but a stuck UI, indexing request or uncertain short-term Google signal does **not** block these enrichment workstreams.

**Source contracts:** [GeoNames dump fields](https://download.geonames.org/export/dump/readme.txt) include population, elevation/DEM and IANA timezone; the [NASA POWER Climatology API](https://power.larc.nasa.gov/docs/services/api/temporal/climatology/) supports point and regional requests, with one parameter per regional request; the [existing Popular-40 method on `main`](https://github.com/michaelgreen06/wet-bulb-35/blob/main/docs/phase2/popular-40-enrichment-pilot.md) pins source versions and visible-copy caveats. Historical source/method gates are tracked separately in PR #41.
